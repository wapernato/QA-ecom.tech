### 1.4. Бонус: рискованный edge case

**Сценарий:** пятый snooze совпадает с переводом часов назад.

Для примера используем интервал snooze **5 минут** и перевод часов **с 03:00 на 02:00**. Пять повторов считаем пятью откладываниями после первоначального сигнала.

Пользователь уже отложил будильник четыре раза. В **02:58, до перевода часов**, он нажимает snooze в пятый раз. Через две минуты часы переводятся на 02:00. Ещё через три минуты наступает `02:03` - прошло ровно пять минут после нажатия.

**Риск:** приложение может назначить сигнал на 03:03, прибавив пять минут к прежнему местному времени. Тогда будильник сработает на час позже. Также перевод часов может ошибочно сбросить счётчик и разрешить больше пяти откладываний.

**Предлагаемое ожидаемое поведение:** отложенный сигнал срабатывает через пять фактически прошедших минут, в 02:03. Счётчик повторов сохраняется, шестое откладывание недоступно. Это правило необходимо согласовать с продукт-менеджером.

**Почему легко пропустить:** snooze и перевод часов обычно проверяют отдельно. Ошибка проявляется при их сочетании, особенно на последнем разрешённом повторе.

### 2.3. Тест-кейсы API

#### 1. Успешное создание заказа

**Требования:** 1, 2, 3, 4.

**Предусловия:** пользователь 15 и товар 101 существуют. Остаток товара 101 составляет 5 единиц. Сервис остатков доступен. Другие запросы не меняют тестовые данные.

**Метод и endpoint:** `POST /orders`.

**Заголовок:** `Content-Type: application/json`.

**Тело запроса:**

```json
{
  "user_id": 15,
  "items": [
    {
      "product_id": 101,
      "quantity": 2
    }
  ]
}
```

**Шаги:** отправить запрос, проверить ответ и найти заказ по полученному ID через доступный API чтения или в базе данных.

**Ожидаемый статус:** `201 Created`.

**Ожидаемый результат:**

- В ответе есть ID нового заказа и статус `created`.
- Создан один заказ пользователя 15 с товаром 101 в количестве 2 единиц.
- ID и статус в ответе соответствуют сохранённому заказу.

#### 2. Некорректное количество товара

**Требования:** 3, 5.

**Предусловия:** пользователь 15 и товар 101 существуют. Остаток товара составляет 5 единиц. Сервис остатков доступен. Единственная ошибка запроса - количество 0.

**Метод и endpoint:** `POST /orders`.

**Заголовок:** `Content-Type: application/json`.

**Тело запроса:**

```json
{
  "user_id": 15,
  "items": [
    {
      "product_id": 101,
      "quantity": 0
    }
  ]
}
```

**Шаги:** отправить запрос, проверить ответ и убедиться, что заказ не появился в системе.

**Ожидаемый статус:** `400 Bad Request`.

**Ожидаемый результат:** запрос отклонён, заказ не создан, остаток товара не изменился. Формат и текст ошибки проверяются после уточнения требований к ответу.

#### 3. Сервис проверки остатков недоступен

**Требование:** 8.

**Предусловия:** пользователь 15 и товар 101 существуют. Тестовая заглушка сервиса остатков настроена так, чтобы на все обращения возвращать 503. Остальные сервисы работают.

**Метод и endpoint:** `POST /orders`.

**Заголовок:** `Content-Type: application/json`.

**Тело запроса:**

```json
{
  "user_id": 15,
  "items": [
    {
      "product_id": 101,
      "quantity": 2
    }
  ]
}
```

**Шаги:** отправить запрос, убедиться по журналу заглушки, что API обращался к сервису остатков, затем проверить ответ и состояние заказов.

**Ожидаемый статус:** `503 Service Unavailable`.

**Ожидаемый результат:** API возвращает 503 и не сообщает об успешном создании заказа. Проверяем, что заказ со статусом `created` не появился. Если сохраняется запись неуспешной попытки, она не должна выглядеть как успешно созданный заказ.

После проверки восстановить работу сервиса остатков и очистить тестовые данные.

### 2.4. Почему недостаточно проверить только HTTP-статус

Ответ 201 сам по себе не доказывает, что заказ сохранён правильно. Например, система может вернуть 201, но записать другое количество товара.

Кроме статуса проверю:

- В ответе есть ID заказа и статус `created`.
- По этому ID действительно находится новый заказ.
- У заказа правильный пользователь, все переданные товары и их количества.
- Один запрос не создал несколько заказов.
- Если при создании предусмотрено резервирование или списание, товар учтён один раз и в правильном количестве.

Для ошибочных запросов проверю не только код ответа, но и отсутствие созданного заказа. После 503 особенно важно проверить фактическое состояние операции: один код ошибки не подтверждает, что все внутренние действия отменены.

### 2.5. Бонус: повтор запроса после обрыва соединения

**Проблема:** сервер мог создать заказ, но клиент не получил ответ. Повторный запрос может создать второй такой же заказ. Если создание заказа резервирует товар, он может оказаться зарезервирован дважды.

Есть и другой случай: первый заказ забрал последнюю единицу товара, а повторный запрос вернул 409. Клиент видит ошибку, хотя первый заказ уже создан.

**Вопросы к команде:**

- Как клиент может узнать результат первого запроса после потери ответа?
- Есть ли защита от повторного создания заказа, например ключ идемпотентности?
- Что происходит, если повтор приходит, пока первый запрос ещё обрабатывается?
- Что возвращать, если тот же ключ пришёл с другим товаром или количеством? Как долго хранится ключ?

**Предложение:** использовать уникальный ключ для одной операции создания заказа, например `Idempotency-Key`. При сетевом повторе клиент отправляет тот же ключ. Если заказ уже создан, сервер возвращает его ID и не создаёт второй. Это предложение, его нужно согласовать с командой.

**Что проверить при согласованной защите от повторов:**

| Проверка | Ожидаемый результат |
| --- | --- |
| Ответ потерян после создания заказа, клиент повторяет запрос с тем же ключом. | Возвращается ID первого заказа, второй заказ не создаётся. |
| Два запроса с одинаковым ключом обрабатываются одновременно. | Создаётся только один заказ. Ответ на запрос, который пришёл во время обработки первого, соответствует согласованным правилам. |
| Сервер перезапустился после создания заказа, затем пришёл повтор с тем же ключом. | Сервер находит результат первой операции и не создаёт дубль. |
| С тем же ключом отправлены другие товары или количества. | Запрос отклоняется по согласованным правилам, первый заказ не меняется. |
| Пользователь намеренно создаёт два одинаковых заказа с разными ключами. | При достаточном остатке создаются два разных заказа. |
| Первый запрос получил 503, затем сервис остатков восстановился и пришёл повтор. | Результат соответствует согласованным правилам повторов после ошибки. Нет дублирующих заказов или резервов. |

Для первого сценария нужно оборвать ответ после подтверждённого сохранения заказа. Простое отключение сети не гарантирует, что проверен именно этот случай. Итог проверяется по числу заказов, их ID и резервам, если они предусмотрены.

## Задание 3. SQL-запросы

Схема таблиц в присланном условии отсутствует. Для запросов использованы следующие названия, которые нужно сверить с исходной схемой:

- `users`: `id`, `name`, `city`.
- `orders`: `id`, `user_id`, `amount`, `status`.

Сумма заказа хранится в `amount`, оплаченный заказ имеет статус `paid`, возвращённый - `returned`. Суммы указаны в одной валюте, поле `amount` заполнено. Используется синтаксис PostgreSQL.

### 3.1. Пользователи из Москвы

```sql
SELECT u.id, u.name, u.city
FROM users AS u
WHERE u.city = 'Москва'
ORDER BY u.id;
```

### 3.2. Сумма оплаченных заказов каждого пользователя, включая пользователей без заказов

```sql
SELECT
    u.id,
    u.name,
    COALESCE(SUM(o.amount), 0) AS total_paid
FROM users AS u
LEFT JOIN orders AS o
    ON o.user_id = u.id
   AND o.status = 'paid'
GROUP BY u.id, u.name
ORDER BY u.id;
```
### 3.3. Пользователи хотя бы с одним заказом returned

```sql
SELECT u.id, u.name, u.city
FROM users AS u
WHERE EXISTS (
    SELECT 1
    FROM orders AS o
    WHERE o.user_id = u.id
      AND o.status = 'returned'
)
ORDER BY u.id;
```

### 3.4. Топ-3 пользователей по сумме оплаченных заказов

```sql
SELECT
    u.id,
    u.name,
    SUM(o.amount) AS total_paid
FROM users AS u
JOIN orders AS o ON o.user_id = u.id
WHERE o.status = 'paid'
GROUP BY u.id, u.name
ORDER BY total_paid DESC, u.id ASC
LIMIT 3;
```
### 3.5. Пользователи без единого заказа

```sql
SELECT u.id, u.name, u.city
FROM users AS u
LEFT JOIN orders AS o ON o.user_id = u.id
GROUP BY u.id, u.name, u.city
HAVING COUNT(o.id) = 0
ORDER BY u.id;
```
### 3.6. Средняя сумма одного оплаченного заказа по каждому городу

```sql
SELECT
    u.city,
    AVG(o.amount) AS avg_paid_order_amount
FROM users AS u
JOIN orders AS o ON o.user_id = u.id
WHERE o.status = 'paid'
GROUP BY u.city
ORDER BY u.city;
```
